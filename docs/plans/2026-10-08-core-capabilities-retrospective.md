## 有效的做法

1. **先出设计，再出计划，各做一轮合并评审。** 两轮评审各发现一个阻断问题，都在动手前修掉了：
   - 设计评审：压缩切点可能把工具调用和它的结果拆开，首条 user 消息和溢出兜底没有定义。
   - 计划评审：T04 让会话用量改由事件汇总，但事件到 T05 才开始记录，按原顺序做，用量会归零。
   这两处如果到实施时才发现，返工都要跨多个任务。
2. **契约先录基线再切换。** T04b 在切换前的提交（fc85a08）上录下 stream-json 的字段集合，作为 golden 文件。整个存储替换完成后，Gofer 依赖的输出没有发生意外变化。
3. **把风险高的任务交给更强的模型。** T11 同时涉及安全边界和 Gofer 契约，改用 opus 实施，主会话再逐行核对审批层的放行逻辑，一次通过。
4. **最后一步用真实二进制冒烟，而不只看单元测试。** 单元测试全部通过的情况下，冒烟仍然发现了本次最严重的缺陷（见下文）。
5. **用 gofer plan 的 todo 和备注留痕。** 每个任务都记下提交号、谁实施的、复核了什么、有哪些偏离，中途压缩上下文后仍能准确接续。

压缩问题的根源是保留量（20k）和预留量（16k）写死为常量，而单元测试只用大窗口。现在改为按窗口比例取值，并补了小窗口的测试。

## 不足与教训

1. **子 agent 用了 `git stash`。** 并行或连续的子 agent 共用一个工作区，stash 会把别人的改动一起藏起来。之后在实施说明里加了“禁止 stash”，后面再没出现。**以后派子 agent 的说明一开始就写上这条。**
2. **说要做却没有做。** 复核 T08 时我说过要改成“先生成摘要、再建会话”，以免失败后留下一个占着 ID 的 archived 会话，但之后没有改，只把它记进了 `suag-iw3u` 第 7 项。实际上这样调整有个约束：摘要的模型调用要记在新会话名下，所以需要先确定会话 ID。这一点当时应该说明，而不是先表态要改。
3. **子 agent 只说测试通过，没有实际运行验证。** 压缩修复的子 agent 只跑了单元测试，真实二进制的复验是我补跑的；T13 改了 YAML 配置样例，也没有校验能否解析。**以后凡是行为修复或配置改动，实施说明里要写明需要实际运行哪条命令来验证。**
4. **平台差异要到 Windows 上才暴露。** 导出测试在 Windows 上断言了文件权限位，结果在主机上失败。涉及文件权限、路径和 socket 的测试，写的时候就应该考虑 Windows。
5. **文档索引漏了更新。** T13 同步了 README、Gofer 使用文档和 AGENTS.md，但 `docs/README.md` 没有加入本次的设计和计划。这次复盘一并补上。
