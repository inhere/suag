## 有效的做法

1. **两轮评审各抓住一个“会变成安全问题”的缺陷，而且都发生在写代码之前。**
   - 设计评审：发现交互确认的读取状态机写错了。按原设计，回合中 cooked/raw 切换、activity 握手、挂起读这几处会导致输入错乱或死锁，Ctrl-C 的实际语义也和设计写的不一致。
   - 计划评审：发现"回合中已经回车的一整行会被当作确认回答"，也就是提前敲好的 `y` 会直接放行。另外发现 Windows 需要的 API 在锁定的 x/sys 版本里不存在。

   这三点任何一个漏到实施阶段，都要返工或留下 fail-open 的口子。
2. **实施者对关键安全性质做了反向验证。** opus 子 agent 做法是：先删掉"丢弃握手字节"的逻辑，确认"提前敲的 y 被当作回答"这个测试会失败，再恢复。这说明测试真的守住了这个性质。
3. **端到端验证用了能确定输入时序的伪终端驱动。** 驱动脚本用 python pty，看到预期输出后再输入，所以能验证"回合中提前打字"这种只有真实终端才会出现的场景。
4. **用户报问题时直接取证据。** 每次都先拿 trace、export 或调试日志定位根因，再做最小修复：
   - reasoning 空值：导出会话，发现某一步的 reasoning 长度为 0；
   - 提示符不刷新：用进程列表证明 hook 进程已经退出；
   - 网页回复没进 chat：请 gofer 查 server 记录，确认请求根本没到 server。

   没有一处靠猜。
5. **小改动按 Quick 直接做，没有走设计和计划。** 宽字符、提示符、着色、显示调整都是根因加最小修改加针对性测试，几分钟到几十分钟就交付了。

| 发现 | 来源 | 如果漏掉会怎样 |

## 不足与教训

1. **驱动脚本的断言写错了一次。** 第一版检查"输出里有没有 SMOKE_OK"来判断命令是否执行，但询问提示本身就会显示这个命令；而且是在整个累计输出里查找，没有从当前步骤开始。结果一项本该失败的检查判成了通过，另一项本该通过的检查判成了失败。**以后端到端断言只检查本步骤之后的新输出，并以结果行为准。**
2. **子 agent 交给用户的生成命令写错了路径。** 计划里重新生成 golden 的命令用的是相对路径，但 `go test` 是在包目录下运行的，按原样执行会写到错误位置。子 agent 实施时发现了这个问题。**以后计划里给出的命令要先实际跑一遍。**
3. **问题最终还是靠用户实际使用才暴露。** 网关请求头、reasoning 空值、宽字符、提示符刷新，这几个问题都是在用户真正用起来之后才发现的。上一次复盘已经写了"涉及 provider 协议的改动要用真实模型试一轮"，这次又因为没有真实终端和真实密钥，部分验证只能交给用户。

## idev-std 在实践中的作用（如实评估）

**起了作用的部分：**

- **强制独立评审。** 本日四份文档各做了一轮评审：配置分层的设计和计划，chat 确认的设计和计划。每轮都有一条 CORE_BLOCKING，而且都是真问题：只读放行无法配置、拆包成环、读取状态机错误、提前输入放行。这是收益最大的环节。
- **人工 Gate 加待确认事项。** 这样会改变用户结果的取舍会显式交给用户决定，例如 Q3"allow_write 是否作用于 run"、旧配置是否兼容、是否删除 `--provider`，避免了实施者自行做安全相关的决定。
- **Quick 与 Full 的分档。** 小修直接做，大改先设计，这让日常修复没有被流程拖慢。
- **实施期发现的分类。** 子 agent 的偏离按 Corrective 记录并说明原因，复核时能快速判断要不要停下。

**成本偏高或作用有限的部分：**

- **规范载荷的重复加载。** 本会话后半段一共加载了 6 次，每次 16–42 KB，状态都是 FULL。原因是每切换一次任务类型（design → plan → implement），驻留状态就变成 STALE，必须整份重读。其中相当一部分资源的哈希和此前读过的完全一致，重读没有带来新信息。
- **文档校验器误报。** 它把 YAML 示例里的 `{{session_id}}` 当成未替换的模板占位符；状态行版本和修订记录不一致也会直接失败。两次都改动了文档内容来绕过，不是修正真正的问题。
- **能力发现三张表和 `host_or_non_offline_action`。** 这几项对这个单仓库个人项目价值有限，主要是在满足格式要求。
- **规范不覆盖的失败点。** 规范不要求在真实环境下验证。本日最影响用户的问题（reasoning、请求头、宽字符）都是在流程之外、靠用户实测才发现的。

**结论：** idev-std 的核心价值在“设计和计划先过一轮独立评审，再经用户确认”，它确实在实施前拦下了几处安全和正确性缺陷。主要成本在载荷重复加载和格式性要求上。建议向规范反馈两点：

1. 同一会话内切换任务类型时，资源哈希相同的部分应允许复用，避免整份重读。
2. 文档校验器应忽略代码块里的 `{{…}}`。

是否提交反馈由用户决定。
