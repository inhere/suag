## 有效的做法

1. **两轮评审各拦下一个阻断问题，都发生在动手前。**
   - 设计评审：去掉内置放行名单后，`--read-only` 会忽略用户配置，导致 Gofer 只读 job 的 MCP 工具全部被拒，而且没有配置能恢复。由此新增了 `tools.read_only_allow`。
   - 计划评审：两个共用符号的落点会造成包循环，测试整文件迁移也无法编译。由此在计划里补了一张"符号与测试落点"表，W1 五步因此都一次编译通过。
2. **纯重构用可比对的证据验收**，而不是只看"测试通过"：
   - 全仓测试名单前后对比；
   - 新旧二进制各命令 `--help` 输出逐字节对比；
   - golden 契约文件内容比对。
   这几项让"行为不变"可以被验证，而不是只能声称。
3. **按风险分配模型。** 涉及安全边界的 T08（MCP 放行、外部命令）交给 opus：一次完成，配置错误时 fail closed，测试覆盖了超时边界。机械移动交给 sonnet。
4. **复核时对照设计逐条核实，而不是只看测试是否全绿。** 子 agent 的测试全绿，但复核仍发现了下面"最值钱的发现"表里的两处偏离。
5. **用户在真实环境里使用，最能暴露问题。** 同日 Windows 实测连续暴露了 6 个单元测试无法覆盖的问题（见下表），每个都是先查 trace 或日志定位、再最小修复。

## 最值钱的发现

| 发现 | 来源 | 如果漏掉会怎样 |
|---|---|---|
| 只读模式的 MCP 放行在去掉内置名单后无法配置 | 设计评审 | Gofer 只读 job 全部失去 gofer 查询工具和汇报工具 |
| `providers` 读取绕过了 `${VAR}` 展开 | T07 子 agent 顺带发现 | 按文档写 `api_key: "${OPENCODE_API_KEY}"` 的用户无法连接 |
| `--model <裸模型名>` 被当作错误，与设计不符 | T06 复核 | 常用的临时切换模型写法不可用 |
| OpenCode Go 要求 `x-opencode-session` 请求头 | 用户实测 | 所有请求被网关拒绝 |
| DeepSeek 思考模式要求回传 `reasoning_content` | 用户实测（trace 定位） | 任何带工具调用的回合都失败 |
| CLI 工作目录默认是 `SUAG_HOME/workspace` | 用户实测 | 工具读不到当前项目，与配置样例的说明相反 |
| 30 步上限直接失败、丢掉已做的工作 | 用户实测（trace 显示并非死循环） | 用户无法让模型了解一个中等规模的项目 |
| 两个 provider 的"流式"都是先生成完整回复再一次性输出 | 用户反馈"卡很久" | chat 体验像卡死 |

## 不足与教训

1. **测试脚本自身的坑浪费了时间，共有三处：**
   - 把 `go build && python … &` 写在同一行，整条命令都进了后台，二进制还没编译完就开始跑测试。
   - 用 `pkill -f <模式>` 清理进程时，误杀了正在执行这条命令的 shell 自身，因为它的命令行也含有该模式。
   - 用 `| head -1` 取 session id 时，管道提前关闭，suag 写输出失败而退出，于是 trace 显示为空，看起来像功能有问题。

   **以后：编译和启动后台服务分开执行；后台服务用后台任务机制管理，并用它的停止功能结束，不要用 `pkill -f`；要读进程输出的完整结果时，不要在管道里截断。**
2. **另一个会话的冒烟测试留下的假服务占用端口长达 9 小时，直到端口冲突才发现。** 原因是冒烟测试结束时没有清理后台进程。**以后：冒烟任务结束前列出并停止自己启动的后台进程。**
3. **`go install` 装出的二进制版本号显示为 `dev`。** 文档写的是 `make install`，我却先用了 `go install`，只好重装。**以后：安装时照项目文档的命令执行。**
4. **最初没在真实模型上试过就交付了。** 上一批的冒烟只用了假服务，DeepSeek 思考模式、网关请求头、工作目录这几处问题，都要到用户真正使用时才暴露。**以后：涉及 provider 协议的改动，至少用一个真实 provider 跑一轮带工具调用的对话；没有可用的密钥时，在交付说明里写明"未经真实模型验证"。**
5. **子 agent 的提交署名不一致。** 实施须知要求统一写 Opus，而 sonnet 子 agent 按自己的实际模型署名。后者更准确，**以后实施须知改为"按实际模型署名"**。
