## 2. 产品定义

Suag 是一个面向个人和小团队的 AI Agent 协作助手。它不是单次问答工具，也不是单一代码代理，而是一个以任务为中心的智能体操作系统：

- 能接收复杂目标，并拆解为可执行任务
- 能组织多个 Agent 或外部 Agent 协作执行
- 能在执行过程中进行追踪、干预、审核和恢复
- 能长期运行，持续跟进任务而不是一次性结束
- 能通过 Web、CLI、IM/Channel 等入口与用户交互
- 能通过协议和适配器对接外部工具，而不是绑定某一个特定 Agent 产品

一句话定位：

> Suag 是一个 Web-first 的本地/自托管 AI Agent 协作控制台，用于把复杂任务交给可追踪、可治理、可持续运行的智能体系统完成。

## 3. 产品目标

### 3.1 核心目标

Suag 需要成为个人或小团队的智能助手，基于 AI Agent 系统处理复杂任务和决策，支持团队协作、任务分配、自动执行、进度跟踪、结果审核和外部系统集成。

### 3.2 目标原则

Suag 的产品设计遵循以下原则：

1. 架构核心简单稳定
   核心运行时、编排层、任务模型和观测链路必须先稳定，再在其上叠加更多能力。

2. 长期任务执行
   系统应能持续运行任务、定时巡检、等待外部响应、挂起恢复，尽量减少人工反复介入。

3. 可观测、可追踪
   用户需要看到任务状态、执行步骤、Agent 分工、工具调用、失败原因和人工干预点。

4. 可学习进化
   系统应能根据任务结果、审核意见和团队反馈优化模板、策略、技能组合和 Agent 配置，但变更必须经过审核后生效。

5. 可扩展
   接口与协议优先，不把系统固化为某一种 LLM、某一类工具、某一个入口渠道或某一个外部 Agent 产品。

6. 外部 Agent 协作
   支持通过 A2A 与远程 Agent 协作，通过 ACP 或本地桥接能力发现并调用本地 `claude-code`、`codex`、`opencode` 等工具。

7. 使用简单
   产品默认可运行、可上手、可观察，不要求用户先搭完整复杂基础设施才能开始使用。

8. 多入口交互
   支持 CLI / Web / IM / Channel 等不同入口，并逐步扩展到文本、图片、视频等多模态交互。

## 4. 目标用户

### 4.1 核心用户

- 个人开发者
  需要一个长期帮自己执行研发、分析、调研、巡检、整合信息的 AI 助手。

- 小型研发团队
  需要把任务交给多个 Agent 或外部 Agent 协作处理，同时保留人工审核和过程追踪。

- AI 工作流操作者
  已经在使用 `claude-code`、`codex`、`opencode`、MCP、脚本工具，希望有统一编排和控制入口。

### 4.2 次级用户

- 运营 / 产品 / 研究型用户
  需要把非编码任务交给 Agent 执行，例如资料收集、日报整理、监控告警处置、渠道消息跟进。

### 4.3 不优先服务的用户

- 需要企业级多租户 SaaS 管理的组织
- 对审计、合规、组织权限模型有重度要求的大型企业
- 只想要一个简单聊天机器人而不需要任务编排的用户

## 5. 核心问题

当前用户在使用 Agent 和外部工具时，普遍面临以下问题：

- 工具很多，但没有统一的任务编排与治理入口
- Agent 会做事，但不容易持续跟进长任务
- 多个 Agent 协作时，过程不可见，难以追责和复盘
- 工具调用和权限边界不清晰，容易越界或失控
- 外部 Agent 能力强，但各自分散，难以接入现有工作流
- 想通过 Web 或 IM 使用 Agent 时，消息路由、状态同步和恢复机制不完整
- 反馈和执行结果沉淀不下来，系统无法持续优化

Suag 需要解决的是：

> 如何把“会回答的 Agent”升级为“能长期执行、能协作、能治理、能持续优化”的任务系统。

## 6. 产品定位与范围

### 6.1 产品定位

Suag 是一个面向个人或小团队的 AI Agent 控制平面与执行系统。

它提供：

- 统一任务入口
- 任务编排与 Agent 协作
- 过程观测与人工干预
- 本地工具、脚本、MCP、外部 Agent 接入
- 长期记忆与任务状态沉淀
- 渠道接入和消息路由

### 6.2 v1 产品定位

`v1 foundation` 的定位不是“功能齐全的终局产品”，而是：

> 一个 Web-first、本地/自托管单实例、支持个人或小团队共享使用的 Agent 基座产品。

它必须先把以下主路径打通：

- 任务提交
- 任务执行
- 过程追踪
- 人工干预
- 团队协作
- 外部工具/外部 Agent 基础对接
- 钉钉渠道接入

### 6.3 v1 默认部署模型

- 本地或自托管单实例部署
- 单工作区共享使用
- 非多租户 SaaS
- 默认信任边界在一个团队或一个操作者域内

## 7. 关键使用场景

### 7.1 Web 控制台发起复杂任务

用户在 Web 中提交一个复杂目标，例如“拆解需求、生成技术方案、安排编码、执行审核、输出结论”。系统自动判断是单 Agent 处理还是多 Agent 团队处理，并在任务视图中实时展示执行状态。

### 7.2 团队模式协作

系统根据目标动态创建角色化 Agent，例如 Architect、Coder、Reviewer，按任务依赖推进执行，并把中间结果回传到主任务上下文。

### 7.3 长期任务与计划性任务

系统通过 Agentic Cron 处理定期巡检、重复检查和条件触发任务。Agent 不只是机械触发，而是先感知、再判断、再执行。

### 7.4 人工干预与审核

当工具连续失败、高风险操作待确认、策略不明确或系统建议调整配置时，任务进入待审核状态，用户通过 Web 控制台处理。(下推事件AG-UI, 交互 A2UI)

### 7.5 外部 Agent 协作

系统既能（通过A2A）把远程 Agent 当作协作节点接入，也能（通过ACP）调用本机已有 `claude-code`、`codex`、`opencode`。外部协作结果被纳入统一任务与追踪体系。

### 7.6 渠道接入

用户可通过钉钉触发任务、接收进度、处理干预请求。Web 仍然是主控制面，钉钉是任务输入和通知的重要渠道。

### 7.7 自进化建议

系统根据历史任务结果、审核结论和团队反馈，提出更优的模板、路由、技能组合或 Agent 配置建议，并通过审核后生效。

## 8. 产品设计原则

### 8.1 Web-first，CLI 为辅

Web 是主控制平面，承担看板、追踪、审核、配置和干预。CLI 保留为调试、单机操作和运维辅助入口。

### 8.2 任务优先，而不是聊天优先

Suag 不是先做聊天再附带任务，而是从任务模型、状态机、执行链路和复盘出发设计。

### 8.3 协议优先，而不是工具绑定

系统优先定义接口和协议边界，让 LLM、工具、存储、远程 Agent、渠道连接器都能替换。

### 8.4 观测优先，而不是黑盒自动化

任何自动化收益都不能建立在“用户完全看不见发生了什么”之上。任务状态、关键步骤、失败原因和人工干预点必须透明。

### 8.5 默认可控，而不是完全自治

Suag 支持自治执行，但高风险操作、自我进化和外部协作必须能被限制、暂停、审核和回放。

## 9. 版本策略

### 9.1 终局愿景

终局形态下，Suag 应是一个可持续运行的 Agent 操作系统：

- 支持本地与远程 Agent 混合协作
- 支持多入口和多模态交互
- 支持工具、技能、工作流和渠道连接器生态
- 支持长期记忆、反馈学习、审核治理和持续优化
- 支持个人到小团队的共享协作

### 9.2 v1 Foundation 必须交付

`v1 foundation` 聚焦以下范围：

- Web-first 控制台
- CLI 辅助入口
- 单实例自托管部署
- 单 Agent 与多 Agent 团队执行基线
- 任务与执行状态可视化
- 基础 HITL 审核与恢复
- 基础内存/SQLite 记忆能力
- 基础 tracing / event / SSE 实时推送
- 工具注册与执行基线
- MCP / Skills 基础集成能力
- 远程 Agent 的 A2A 接入抽象
- 本地外部工具的 ACP / CLI bridge 抽象
- 钉钉渠道作为首个正式外部入口
- 自进化建议生成与审核生效机制

### 9.3 v1 明确不承诺完整交付

以下能力属于后续版本或仅做接口预留：

- 多租户 SaaS
- 完整的组织权限与细粒度 RBAC
- 丰富的渠道矩阵
- 多模态处理闭环
- 自动自我修改并直接上线
- 大规模插件市场与生态分发
- 企业级审计、配额、结算与租户管理

### 9.4 阶段性路线

#### Phase A：Foundation Runtime

目标：打通单实例运行时、任务模型、Agent 基础执行、观测和干预链路。

#### Phase B：Collaboration & Tooling

目标：打通团队执行、MCP/Skills、外部 Agent 适配和更稳定的工作区隔离。

#### Phase C：Web Console & Channel

目标：把 Web 控制台做成主入口，并交付钉钉接入。

#### Phase D：Learning & Governance

目标：交付审核式自进化、配置建议与策略优化机制。

## 10. v1 用户旅程

### 10.1 主旅程

1. 用户打开 Web 控制台
2. 提交任务目标，选择自动模式或指定团队模式
3. 系统创建任务，分配 Trace ID，开始执行
4. 用户在任务详情页实时查看步骤、工具调用、Agent 协作和事件流
5. 若遇到高风险或失败，系统进入 HITL，通知用户处理
6. 任务完成后，系统展示结果、产出物、执行摘要和复盘信息
7. 若系统识别到优化空间，可生成配置/技能调整建议，等待审核

### 10.2 渠道路径

1. 用户在钉钉发起任务或接收任务提醒
2. 系统把消息路由到对应会话/任务上下文
3. 钉钉侧承载轻交互和通知
4. 复杂追踪、审核、配置操作回到 Web 控制台完成

## 11. 成功标准

### 11.1 产品层指标

- 用户能够在 10 分钟内完成首次部署和首次任务运行
- 用户能够在 Web 中看到完整任务状态和关键执行步骤
- 用户能够在不依赖 CLI 的情况下完成主要任务发起、查看和干预
- 多 Agent 协作任务可被追踪和复盘
- 系统可把外部 Agent 与本地工具纳入统一任务链路

### 11.2 体验层指标

- 任务的状态变化对用户是可感知的
- 高风险动作不会静默执行
- 任务失败后可以定位原因并恢复，而不是只能重新来过
- 钉钉接入能承载真实任务触发和通知闭环

### 11.3 系统层指标

- 核心运行时在单实例下可稳定执行长期任务
- 关键事件可追踪、可回放、可关联到任务和 Agent
- 自进化建议不会绕过审核直接生效

## 12. 核心产品决策

### 12.1 Web-first

Web 控制台是主产品形态，CLI 是运维和调试辅助，不把 CLI 作为主控制台。

### 12.2 单实例优先

先把单实例自托管模型做扎实，而不是过早进入多租户 SaaS 架构。

### 12.3 A2A 与 ACP 分工

- A2A：用于远程 Agent 与 Suag 之间的协作通信
- ACP / 本地桥接：用于发现和操作本地已安装的 Agent 工具

### 12.4 审核式自进化

自进化在 `v1` 中不是“自动改自己”，而是“自动提出建议并提交审核”。

### 12.5 渠道优先级

`v1` 的首个正式外部渠道为钉钉，其它渠道后续扩展。

---

## 13. 风险与挑战

- 复杂目标容易导致范围膨胀，必须持续保持 `v1` 聚焦
- 外部 Agent 协议和本地工具桥接抽象如果做得过重，会拖慢核心基座交付
- Web-first 会把前端信息架构、观测体验和任务可视化质量推到更高优先级
- 长期任务和自进化能力会引入更多状态一致性、审计和治理要求
- 钉钉接入意味着消息路由、签名校验、通知时效和用户身份映射都要明确
