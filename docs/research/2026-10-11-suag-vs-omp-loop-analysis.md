# suag 与 omp 同任务耗时与用量差异分析（2026-10-11）

issue：suag-jz0l。任务：T9 定时组件（同一说明 `tmp/jz0l-brief.md`，注明主机无 cgo），同一模型 `opencode-go/deepseek-v4.1-flash`，各自独立 worktree（基线 202bfa0），suag v0.11.0。

## 数据

| | suag（job 20261011-231517-edce74d4） | omp（job 20261011-231517-5a5a9ffe） |
|---|---|---|
| 模型调用 / 工具调用 | 58 / 58 | 13 / 16 |
| 工具分布 | shell 27、read 11、edit 14、write 2、list 2、memory 2 | bash 11、read 2、write 2、edit 1 |
| token 合计 | 3.91M | 430k |
| 未命中输入 / 缓存读 / 输出 | 104k / 3.73M / 70.4k | 36.5k / 366k / 26.8k |
| 每次请求平均输入 | 66k（6k → 93k） | 约 31k |
| 耗时 | 628s（模型 589s、工具 37s） | — |

suag 会话历史的体积构成（字符）：思考内容 46.6%、工具参数 37.3%（整文件写入两次共约 42k 字符）、工具结果 14.1%、其余 2%。omp 同样开启思考（`thinking` 块经 `reasoning_content` 回传）。

上一次（T9 原始对比，suag v0.10、无环境说明）：suag 79 次调用、6.49M token、1038s，其中生成输出 776s，3 次 15–17k token 的整文件写入共约 340s。

## 结论

token 差 9 倍 ≈ 调用次数 4.5 倍 × 每次上下文 2 倍；耗时主要花在生成上，同样随步数增长。

1. **步数多是主因**：suag 每步只调一个工具（探索 9 步、写完后连续 6 次单处编辑、调试中 8 次读回自己刚写的文件），omp 一轮内并行多个调用、编辑次数少得多。suag 的工作约定写着“Read a file before changing it; prefer small exact edits”，`file_edit` 一次只能改一处，这两点都在鼓励小步多次。
2. **上下文翻倍**：每步的思考内容与整文件写入的参数都留在历史里，每次请求重发（缓存命中 95% 以上，所以花费不大，但处理与首字延迟随之增长）。
3. **跑偏动作**：`gofer issue list`（受项目规则影响）、写入又删除一条记忆（写进了 worktree 的 `MEMORY.md`，超出任务允许的范围）。

## 改进建议（按收益/成本排序）

1. 提示词约定：相互独立的读取、搜索、命令放在同一次回复里并行调用；刚写过的文件不必再读；执行任务时不主动维护 tracker / 记忆，除非用户要求。（Quick）
2. `file_edit` 支持一次多处编辑（`edits` 列表，逐条精确匹配、整体原子写入）。
3. 上下文：段内保留思考内容与写入参数（不破坏缓存），在分段断点把更早的思考内容与整文件写入参数折叠为摘要（例如“已写入 path，N 行”）；先实测网关是否接受空的 `reasoning_content`。
4. 把本任务固化为评测里的“长编码任务”，对比调用次数、token、耗时，用来验证以上改进。

| 配置 | 验收通过 | 模型调用 | 工具调用 | prompt 总量 | 耗时 |
|---|---|---|---|---|---|
| 改动前（v0.11.0） | 1/2 | 23、38 | 24、38 | 1.03M、1.26M | 418s、335s |

- 两次验收失败都是注入的验收测试跑满 5 分钟超时（实现在回调重入时死锁）。
- 减少步数的约定没有效果：改动后读文件 18/10、编辑 12/16 次，反而更多；工具与模型调用仍接近 1:1，omp 也一样，并行调用看起来是模型习惯，提示词改变不了。
- “执行任务时不维护 tracker/记忆”可能有效：改动前一轮写过记忆，改动后两轮都没有（样本少）。
- 独立任务上 suag 与 omp 同一量级；T9 中 9 倍的差距更可能来自在 suag 仓库内执行（项目规则、记忆、仓库探索），需要单独实验。
- 单配置两轮之间波动接近一倍，结论需要更多样本。

## 补充：仓库内实验与修正（2026-10-12）

任务 `repo-t9-schedule`（评测仓库模式，基线 202bfa0，说明同 T9），同一模型，每组 3 轮；数据在 `tmp/eval/f3-*`、`f4a-*`、`f5-*`、`f6-*`。

### 实验结论（F3）

| 配置 | 通过 | 模型调用 | prompt 总量 | 耗时 |
|---|---|---|---|---|
| suag v0.11.0+ | 2/3 | 54.0 | 3.09M | 604s |
| suag `--no-project-rules` | 3/3 | 57.7 | 3.69M | 665s |
| omp | 1/3 | 28.3 | 1.36M | 432s |

去掉项目规则后步数没有减少，规则不是原因。逐步回放 suag 的工具序列，找到三个 suag 自身的问题：

1. **PowerShell 表格输出被丢弃**（主因）：`shell_exec` 在命令后紧接 `exit`，`Get-ChildItem`、`Select-Object` 这类隐式表格格式化有约 300ms 延迟，输出还没写出进程就退出了，模型拿到空结果、退出码 0，只能换写法反复重试（`cmd /c dir`、`findstr` 等），查依赖库 API 一项每轮多 10–18 步。pwsh 7 与 Windows PowerShell 5 都复现。omp 在主机上用 bash，没有这个问题。
2. **单点编辑多**：每轮 `file_edit` 10–14 次，同一文件常连续 4–8 次。
3. **评测不公平**：suag 在隔离 HOME 下没有 git 身份，提交失败后多花 2–3 步；omp 用真实 HOME。

### 修正

| 提交 | 内容 |
|---|---|
| 672ead3 | 命令块经 `Out-Default` 输出完再退出；关闭 pwsh ANSI 颜色 |
| 7f960ea | `file_edit` 支持 `edits` 列表，一次多处、全成或全不改 |
| 377cf64 | 评测仓库写仓库级 git 身份 |
| 7bbf59f | 工具参数字符串里的原始制表符等控制字符转义后再解析（F5 中一轮因此整次失败） |
| e8fcb68 | 空响应（只有思考内容）重发同一请求，最多 2 次（F6 中一轮因此整次失败） |

- 调用 −21%、prompt −21%、耗时 −14%；连续单点编辑从最多 4–8 次降到 2–3 次，模型会主动用 `edits`。
- `tools.shell` 换成 Git Bash（F6，3 轮）：调用 38.7 对 PowerShell 39.7，没有差别，Windows 默认 shell 不改。
- 仍比 omp 多约 1.5 倍调用：主要是 `file_read` 8.4 次对 omp 的 3 次（omp 常在一条 bash 里 `cat` 多个文件）、shell 23 次对 18 次；suag 在完成后反复验证（`-count=20`、读 CI 配置、按 AGENTS.md 拆文件）更多，验收通过率 9/10 对 omp 1/3。
- 同配置三轮之间调用数从 14 到 57 不等，单组 3 轮的差异需谨慎解读。
