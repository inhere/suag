|---|---|---|

suag 会话历史的体积构成（字符）：思考内容 46.6%、工具参数 37.3%（整文件写入两次共约 42k 字符）、工具结果 14.1%、其余 2%。omp 同样开启思考（`thinking` 块经 `reasoning_content` 回传）。

上一次（T9 原始对比，suag v0.10、无环境说明）：suag 79 次调用、6.49M token、1038s，其中生成输出 776s，3 次 15–17k token 的整文件写入共约 340s。

## 结论

token 差 9 倍 ≈ 调用次数 4.5 倍 × 每次上下文 2 倍；耗时主要花在生成上，同样随步数增长。

1. **步数多是主因**：suag 每步只调一个工具（探索 9 步、写完后连续 6 次单处编辑、调试中 8 次读回自己刚写的文件），omp 一轮内并行多个调用、编辑次数少得多。suag 的工作约定写着“Read a file before changing it; prefer small exact edits”，`file_edit` 一次只能改一处，这两点都在鼓励小步多次。
2. **上下文翻倍**：每步的思考内容与整文件写入的参数都留在历史里，每次请求重发（缓存命中 95% 以上，所以花费不大，但处理与首字延迟随之增长）。
3. **跑偏动作**：`gofer issue list`（受项目规则影响）、写入又删除一条记忆（写进了 worktree 的 `MEMORY.md`，超出任务允许的范围）。

## 改进建议（按收益/成本排序）

1. 提示词约定：相互独立的读取、搜索、命令放在同一次回复里并行调用；刚写过的文件不必再读；执行任务时不主动维护 tracker / 记忆，除非用户要求。（Quick）
2. `file_edit` 支持一次多处编辑（`edits` 列表，逐条精确匹配、整体原子写入）。
3. 上下文：段内保留思考内容与写入参数（不破坏缓存），在分段断点把更早的思考内容与整文件写入参数折叠为摘要（例如“已写入 path，N 行”）；先实测网关是否接受空的 `reasoning_content`。
4. 把本任务固化为评测里的“长编码任务”，对比调用次数、token、耗时，用来验证以上改进。

## R3 结论：token 差距从哪来，输出转存为什么不起作用（2026-10-12）

当前版本（bc7aa12）与 omp 在 T9 上各跑一轮并保留会话（job 20261012-140855-21ccb4b1 / 20261012-140855-54852d5b），统计最后一次请求重发的历史构成：

| | suag | omp |
|---|---|---|
| 最终历史（字符） | 269k | 267k |
| 思考内容 | 58.3% | 72.4% |
| 工具参数（主要是整文件写入） | 19.2% | 16.0% |
| 工具结果 | 18.6% | 10.1% |
| 最大的单条工具结果 | 7.1k（file_read） | 10.4k（grep） |
| 模型调用 / prompt 总量 | 36 / 1.64M（通过） | 20 / 1.19M（未通过） |
| 未命中输入 + 输出 | 83.7k + 59.4k | 86.8k + 67.0k |

二期 5 轮对 omp 3 轮的均值：prompt 2.69M 对 1.36M = 调用 44.0 对 28.3（1.55 倍）× 每次上下文 61k 对 48k（1.28 倍）；其中缓存读占约 96%，按价格计的未命中输入 + 输出为 173k 对 106k（约 1.6 倍）。

1. **prompt 总量的差距主要来自调用次数**：每次调用都重发整段历史，总量约等于“各步历史体积之和”，随步数近似平方增长。两边任务结束时的历史体积几乎相同（约 268k 字符），每步结构也相同（工具与模型调用接近 1:1）。
2. **输出转存几乎不起作用是结构性的**：历史的大头是模型自己产出的思考内容（58–72%）和整文件写入参数（16–19%），工具结果只占 10–19%，且单条都在内联阈值（8000 字节）以下，这一轮 suag 一次都没有触发转存。`file_read` 本身分页、不转存。转存解决的是“偶发的超大输出撑爆上下文”，不是常态消耗。
3. **单轮波动大于两者差距**：这一轮 suag 36 次调用、未命中 + 输出反而比 omp 少；均值上的差距主要是 suag 完成后验证更多、对自己写的文件分段续读更多（见二期一节）。
4. **能明显降低常态消耗的只有一处：历史里的思考内容与整文件写入参数**。两者都只对当时那一步有用，后续步骤每次都重发。

### 改进建议

- **历史折叠（建议出设计）**：在断点把较早步骤的思考内容去掉、把整文件写入参数换成“已写入 path，N 行 / N 字节（需要时重读文件）”。折叠会让一次请求的缓存前缀失效，所以只在断点做（段切换、每 N 步、或累计可折叠体积超过阈值），用一次未命中换后续每步的重发量。前置实验：
  1. 网关与模型是否接受去掉较早步骤的 `reasoning_content`（DeepSeek 思考模式在工具调用链中要求回传，需确认只保留最近几步是否可行）；
  2. T9 上 A/B（不折叠 / 每 N 步折叠），看 prompt、未命中、通过率与耗时，每组至少 3 轮。
- 与 suag-kxlq（空闲整理）与分段设计同属“投影在断点重算”，一并设计。
- 步数（验证与续读多）属于提示词与约定层面的取舍，此前实验显示约定改不动模型的单步习惯，暂不再投入。

## 历史折叠实验（2026-10-12，plan-20261012-142202-6ecdb35f）

实验开关 `context.fold_every` / `context.fold_keep`（cb35c89，默认关）：请求视图中边界之前的助手步骤去掉思考内容，超过 1000 字符的字符串参数换成一句说明；边界每 N 步前移一次，缓存前缀只在批次切换时失效；存储的历史不变。

**网关**：每 2 步折叠、保留 1 步的激进设置跑 3 个多步任务，都没有 provider 错误（网关接受清空的旧 `reasoning_content`），模型行为正常。

**T9 A/B**（command-code/deepseek/deepseek-v4.1-flash，同一二进制，两组并行各 3 轮，均未设思考档位）：

| | 通过 | 模型调用 | prompt 总量 | 每次请求 | 未命中输入 | 缓存读 | 输出 | 耗时 |
|---|---|---|---|---|---|---|---|---|
| 不折叠 | 0/3 | 61.3 | 4.48M | 73.0k | 108k | 4.37M | 78.5k | 978s |
| 折叠（每 10 步，保留 5 步） | 2/3 | 49.0 | 1.82M | 37.1k | 160k | 1.66M | 66.1k | 640s |

- 每次请求的上下文减半（−49%），prompt 总量 −59%，耗时 −35%。
- 代价是未命中输入 +48%（每次边界前移，之后的前缀要重新缓存）。按缓存读价格为未命中的 1/10 折算，输入侧等价成本 545k → 326k（−40%）；缓存读按 1/4 折算也是 1.20M → 0.58M。输出也略少。
- **更正（2026-10-12）**：DeepSeek flash 的缓存命中价约为未命中价的 1/50（DeepSeek-Reasonix 价目表：0.0028 对 0.14 USD/M）。按 1/50 折算输入侧为 108k + 87k ≈ 195k 对 160k + 33k ≈ 193k，**成本基本持平**；折叠的收益在耗时（−35%）与每次请求的上下文体积，不在 DeepSeek 上的费用。缓存读价格占比更高的 provider（如 1/10、1/4）上才省钱。
- 通过率没有变差：不折叠组 3 轮都失败在同一个验收用例（取消运行中的任务未生效），折叠组 1 轮是验收测试超时（观察者重入死锁）。样本小，不把通过率差异归因于折叠。
- 调用数 61 → 49 可能有折叠后上下文更短的作用，也可能是波动；同配置单轮之间调用数相差一倍是常态。
- 两组都未设思考档位（provider 默认）；omp 以 `reasoning_effort: high` 运行，与 omp 的对比需在同一档位下重做（`--thinking`，57f5203）。

**结论**：折叠在 T9 上以少量额外未命中换来上下文减半、总量与耗时大幅下降，值得做成正式功能。需要设计的问题：默认参数与开关、与分段/压缩/空闲整理的关系（同属“投影在断点重算”）、折叠说明文案对模型行为的影响、可观测性（trace 记录每次折叠）、长输出的工具结果是否一起折叠。

## 同模型同档位对比（2026-10-12，v0.13.0，plan-20261012-170528-16551533）

两边都用 command-code 的 `deepseek/deepseek-v4.1-flash`、`--thinking high`（此前的对比 omp 以 high 运行、suag 未设档位），T9 各 3 轮并行；suag 为 v0.13.0（历史折叠默认开启）。

### 可参考的做法（按对 suag 的预期收益排序）

1. **编辑结果带紧凑 diff**（pigo）：模型看得到改后的内容，减少“改完再读”。suag 的 `file_edit` 只返回替换次数。
2. **测试/构建输出聚合成明确的 PASS/FAIL 摘要**（pi-go、oh-my-pi）：让“通过就停”有明确依据，也压缩上下文。
3. **条件触发的一次性提醒**（pigo）：例如编辑后测试通过时提示“检查已通过，可以收尾”，不进历史；直接针对全绿之后的多余验证。
4. **卡死检测 + 告诉原因后继续**（pi-go）：同调用同结果重复、同工具连续失败时注入说明，而不是只靠 MaxSteps。
5. **只读批量并行执行**（pigo）：整批只读时并发、按序回填；降低每步耗时，让一次发多个调用更划算。
6. **观测补充**（pi-go、pigo）：每次运行一条固定格式的汇总（与 `trace --analyze` 同源），可选导出 OTEL gen_ai span；可加入“结果重复的调用”计数。
7. 低成本项：结果去重（相同只读结果换成指针）、长命令转后台 + wait/kill、回复被截断时不执行残缺参数、参数别名与类型纠正。

## 主流 agent 源码对照：减少步数的机制（2026-10-12）

只读阅读源码（WP `tmp/refs/`）：oh-my-pi `3a9b01d`、DeepSeek-Reasonix `9c37134`、openai/codex `6e5f665`、block/goose `4617040`、sst/opencode `bcf23b6`、cline/cline `8eba11b`，加上一节的 pi-go 与 pigo。各项附具体文件与行号的原始报告未入库，结论如下。

**omp 为什么少一半调用**：差距主要不在提示词（suag 已有意思相近的约定，L3 也证明约定改不动模型），而在**工具结果本身给出可信证据**。DeepSeek 在 omp 里使用 `replace`（old/new）编辑模式，与 suag 可比。

- 编辑结果带行号的紧凑 diff 预览，编辑前能解析、编辑后不能时当场警告“introduced a syntax error near line N”（tree-sitter）。
- `write` 后默认跑 LSP 诊断并把结果放进返回值：新写的 Go 文件不用跑 build 就能看到编译错误。
- shell 输出 minimizer 默认开启：`go test` 全部通过压成一行 `go test: N packages ok`，失败只留 FAIL 与定位行（头 140、尾 80 行）；内联上限 50KB 取尾部，提示词禁止 head/tail。
- 读取：不带范围读 100 行以上的代码文件时返回声明大纲和被省略的精确行段；同一输出连续 3 次追加“再读也不会变”。
- 上下文剪枝：同一文件被完整重读后，旧读取结果换成 `[Superseded by a newer read of this file]`（避开已热的缓存前缀）。
- 卡死检测：连续 5 轮规范化后完全相同的调用，注入“NEVER call … with those arguments again”。
- 并行：只读工具默认 shared，同一响应内全部并发；edit/write/todo 为 exclusive。
- 截断（stop=length）时不执行本轮调用，给每个调用一个占位结果，要求拆成小调用。
- 参数自动修复：双重编码的 JSON、扁平化数组、null 占位、枚举空白；工具名错时给 “Did you mean”。

**各家共同做法**（出现于两家以上）：

| 机制 | 出处 | 对应 suag 的问题 |
|---|---|---|
| 编辑结果带 diff / 改动处片段；失败时给最相似片段与行号 | omp、pigo、Cline；goose（失败提示） | 读自己文件 4–12 次；`file_edit` 失败提示“re-read the file” |
| 测试/构建输出压成明确的 PASS/FAIL 摘要 | omp、pi-go | 全绿之后 15–27 步 |
| 写后诊断（LSP/编译） | omp、pi-go | 写完再单独跑 build/vet |
| 只读工具并发执行、结果按调用顺序回填 | omp、codex（读写锁）、Reasonix（上限 8）、pigo、opencode（边流式边执行） | 每步耗时；suag 串行 |
| 旧读取结果被新读取/编辑取代后作废（批量改写以保护缓存） | omp、Cline、pi-go | 重复读的内容一直留在上下文 |
| 重复调用检测，先提醒后升级 | omp（5 轮）、Cline（3 次软 / 5 次硬）、pi-go、goose | 重复跑同一条测试命令 |
| 截断回复不执行残缺调用，要求拆分重发 | omp、pigo、Reasonix、Cline、opencode | 残缺参数被执行或整次失败 |
| 参数错误逐个调用回给模型，不中断整轮 | codex、goose | suag 缺必填参数时整次运行失败 |
| 长命令转后台 + wait/kill | codex、pi-go、pigo、opencode、Cline | 超时即杀、重跑 |

**DeepSeek 专项**（Reasonix）：缓存命中优先读 `prompt_cache_hit_tokens`，退到 `prompt_tokens_details.cached_tokens`（suag 只读后者，直连 DeepSeek 会算成 0）；`reasoning_content` 只在带 tool_calls 的助手消息上回传；发送前修复未应答的 tool_call 与截断的参数 JSON；对缓存未命中做归因（逐消息累计哈希，定位是 system、tools 还是 fold 改变了前缀）。

**观测**：omp `stats` 按请求记录耗时/TTFT/stop_reason/缓存，工具记录 `calls_in_turn`、参数与结果字符数，trace 视图汇总 modelMs/toolMs/idleMs；opencode 用 SQL 汇总每个工具的成功/失败/未完成与耗时；codex 把工具耗时拆成“等待调度”与“实际执行”；pi-go/goose 走 OTEL gen_ai span。

### suag 改进清单（按预期收益排序）

1. **`file_edit` 结果带改动处的行号片段**（必要时限长），Go 文件附 `go/parser` 解析回归警告；失败时返回最相似片段与行号，不再只说“re-read the file”。
2. **shell 输出摘要**：识别 `go test/build/vet`（可扩展到其他测试命令），全部通过压成一行，失败只留 FAIL 与定位行；原文仍转存可取。

6. **反重复**：旧读取结果作废（批量改写保护缓存）、同一调用重复 N 次时注入提醒。
7. **写后诊断**（Go：编辑后对所在包跑 `go vet` 或 `gofmt -e`，可配置）。
8. **观测**：工具耗时拆分、缓存未命中归因、每次运行一条固定格式汇总，接入 `trace --analyze` 与后续 `trace --web`（suag-nmed）。
