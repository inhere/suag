# Suga

[![Unit-Tests](https://github.com/inhere/suga/actions/workflows/go.yml/badge.svg)](https://github.com/inhere/suga/actions/workflows/go.yml)

English | [简体中文](README.zh-CN.md)

Suga is a personal coding agent written in Go. One persistent conversation engine serves two interfaces: a terminal CLI (`chat` and one-shot `run`) and an ACP stdio server (`acp`). [Gofer](https://github.com/inhere/gofer) can launch either one and adds jobs, workers, logs and interactive approval on top.

- **Development tools**: read files in line windows, list, grep and find files, edit by exact replacement, run shell commands (PowerShell on Windows), fetch web pages, search the web.
- **Safe by default**: read-only unless writing is enabled; chat asks before writing or running commands; file tools stay inside the workspace; web fetches refuse private networks.
- **Skills**: standard `SKILL.md` skills from the workspace, `~/.suga/skills` and `~/.agents/skills`, listed or searched on demand; a built-in configuration and usage guide skill, `suga-guide`.
- **Persistent sessions**: one SQLite database with resume, automatic compaction, plans, handoff and an event log for tracing and stats.
- **MCP**: stdio MCP servers with allowlists and deferred loading for large tool sets.
- **Persistent memory**: user and project memory that outlives sessions. Plain `MEMORY.md` files are the source of truth, and the backend can be swapped (files, gofer or an external command).
- **History search**: full-text search over earlier sessions, and paging through saved tool output.
- **Large-output offloading**: oversized tool results are saved under the session directory; the context keeps only the head, the tail and a ref.

## Install

Requires Go 1.26+. The repository is private, so build from a checkout:

```bash
git clone https://github.com/inhere/suga.git && cd suga
make install            # or: go install ./cmd/suga
```

`make install` builds (compressing with `upx` when available) and installs to `$(go env GOPATH)/bin`. On Windows it first moves aside a binary that a running chat is still using. With access to the repository configured (`GOPRIVATE=github.com/inhere/*`), `go install github.com/inhere/suga/cmd/suga@latest` works too. Pushing a `v*` tag runs the release workflow, which attaches prebuilt binaries for Linux, macOS and Windows. Make sure the install directory is on the `PATH` of your shell (and of the Gofer server, if you use it), then check `suga version`.

## Quick start

Create `~/.suga/config.yaml` (see [config/config.yaml](config/config.yaml) for every field):

```yaml
model: deepseek/deepseek-chat   # <provider>/<model>
# providers: openai, anthropic and deepseek are built in and read
# OPENAI_API_KEY / ANTHROPIC_API_KEY / DEEPSEEK_API_KEY.
tools:
  allow_write: true             # let chat write files and run commands (asks first)
```

```bash
suga chat                                         # interactive chat in the current directory
suga run --prompt "Summarize this project"        # one turn, read-only
suga run --allow-write --prompt "Fix the failing test"
suga run --resume <session-id> --prompt "Continue"
suga run --max-steps 30 --prompt "Long task"      # this turn's step limit
```

A turn uses at most `max_steps` steps (default 240) and is then asked for an answer from what it has. `run --max-steps N` (N ≥ 1) overrides that for one invocation; `SUGA_MAX_STEPS` is checked in between, and sub-agents keep their own `agents.max_steps`.

In chat, `:session` shows the session id, `:compact` starts a new segment (see [Sessions](#sessions)) and `:quit` (or `:exit`) leaves. `:add-dir <absolute directory>[:ro|:rw]` authorizes another directory for this session, `:dirs` lists the workspace and every added directory with its mode and where it came from (the flag, `SUGA_ADD_DIRS`, typed in chat, authorized at a question, or kept from an earlier process) and `:rm-dir <path>` revokes one; the change is recorded in the session, so it holds for the rest of the chat and for a resume. Those commands only work when typed at this terminal: text delivered by `suga send` or a job runner is always an ordinary message, so a delivered `:add-dir` (or `:quit`) can never act on the session. Pressing Ctrl+C once at the prompt clears the line; pressing it again within 3 seconds exits. Ctrl+D exits immediately. On exit chat prints token usage and the command that resumes the session. Continuing an existing session (`--resume <id>`, or `--session-id <id>` naming one that exists) first shows the last reply the model gave with text, above the first prompt, so you can go on from it: a dim "上一次回复：" (last reply) sets it apart, a long reply is cut to its last 40 lines with the `suga trace` command for the rest, and a turn that was interrupted or failed is marked "上一回合未正常结束" (the previous turn did not end normally). It only reads: no model call, no session entry. A session a killed process left in `running` (kill -9, a crash) is recovered by the first prompt after the continue - chat prints "上一回合异常中断，已恢复会话" and the interrupted turn is recorded `cancelled`, so the new turn can start; a session a live process is inside is still refused, as before.

## Configuration

Suga reads only `$SUGA_HOME/config.yaml` and `$SUGA_HOME/.env` (default `~/.suga`); the working directory's config and `.env` files belong to your project and are never read. `SUGA_CONFIG` selects one config file. Secrets go into `$SUGA_HOME/.env` (e.g. `BAILIAN_API_KEY=...`); a `${VAR}` in the config is expanded from there or from the process environment. The settings used most:

| Setting | Meaning |
|---|---|
| `model` | Main model, `<provider>/<model>`; overridden by `SUGA_MODEL`, then `--model` |
| `providers.<id>` | `type` (`openai` = chat/completions, `openai-responses` = Responses API, `anthropic`), `base_url`, `api_key`, `headers`; the presets `openai`, `anthropic` and `deepseek` are built in and read `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY` |
| `providers.<id>.models.<model>` | `context_window`, `model_id` (the id sent to the provider when it differs from the key), `type`/`base_url` (a model may use its own protocol), `price`, `thinking` |
| `compact_model`, `fallback_models` | Cheaper model for summaries; models tried in order when the main one fails |
| `tools.allow_write`, `tools.approval` | Chat only: enable write and shell tools (default false); `ask` (default) confirms every write and shell call, `auto` does not |
| `mcp.servers`, `tools.auto_allow`, `tools.read_only_allow` | MCP servers, and the MCP allowlists (`server/toolglob`); every MCP call is refused while both are empty |
| `memory.user.backend`, `memory.project.backend`, `memory.write_tainted` | Memory backend per scope (`files`, `gofer` for the project, `exec`) and what a session that read external content does on a write (`ask`, `deny`, `allow`) |
| `hooks.command`, `hooks.post_tool_use` | Chat hook command (an argv list) and which tool calls get a PostToolUse event; no `hooks.command`, no hooks |
| `skills.list_max`, `skills.always_load` | How many skills are listed with their description; skills whose body goes into every prompt |
| `workspace` | Workspace root of the file and shell tools (default: the directory suga was started in) |

Everything else — every setting with its default, the provider and model details, and a step-by-step setup guide (choosing a provider, writing `config.yaml`, putting the key in `.env`, checking the first run, reading the errors) — is in the built-in **suga-guide** skill, released on the first run to `~/.suga/skills/suga-guide/`. In chat you can simply ask how to configure suga; the model loads that skill and answers from it.

All data lives in `$SUGA_HOME/db/sessions.db`.

## Tools and permissions

| Tool | Kind | What it does |
|---|---|---|
| `file_read` | read | Numbered lines in windows (`offset`/`limit`, 2000 lines by default); `paths` reads up to 10 files in one call; reports binary files |
| `file_list` | read | Directory listing, recursive with `depth` (≤ 5) |
| `file_grep` | read | RE2 search with `glob`, `ignore_case`, `output: content\|files` |
| `file_find` | read | `**` glob search, newest first |
| `web_fetch` | read | Page text (headings, links and code kept); private and local addresses refused |
| `web_search` | read | SerpAPI search (needs `serpapi_key`) |
| `skill` | read | Load a skill, read its files, or search skills (`query`, `"*"` lists all names) |
| `session_search` | read | Full-text search of earlier messages, tool results and summaries (`scope`: workspace, current, all); with `ref=out:...` it searches inside one saved output |
| `recall` | read | Read around a hit by ref: messages from `<session>/<seq>`, or numbered lines of a saved output `out:<session>:<hex>` |
| `agent` | read | Hand one self-contained task to a sub-agent that reads widely in a context of its own and returns only its report (`description`, `prompt`, `type`: `explore` or `research`, `background`); see [Sub-agents](#sub-agents) |
| `suga_manifest` | read | This instance's capabilities as JSON (same data as `suga manifest`) |
| `memory` | state | `add`, `replace`, `remove`, `get`, `search` on long-term memory (`scope` project or user); see [Memory](#memory) |
| `file_write` | write | Write a whole file |
| `file_edit` | write | Replace an exact, unique string (or all with `replace_all`), or several with `edits` in one call (all or nothing); keeps CRLF |
| `file_remove` | write | Remove a file, or a directory with `recursive`: moved to `$SUGA_HOME/trash/` and kept 7 days (`origin.json` records where it came from), at most 1000 files per call. Directories ignored by `.gitignore` (and `node_modules`, `vendor`, `dist`), such as a test repository under an ignored `tmp/`, are regenerable: deleted for good without being walked or counted, and listed in the result. Ignored single files like `.env` still go to the trash. Refuses the workspace root, its own `.git`, the home directory, wildcards and paths outside the workspace |
| `shell_exec` | write | Run a command (PowerShell on Windows, `sh` elsewhere) with a timeout; returns output and exit code. In `run` and chat, `background: true` starts it as a background task and returns a task id at once |
| `task` | state | The session's background tasks: `list`, `output` (the last lines, `offset`/`limit`, `grep`), `wait` (with `timeout`), `kill` (the whole process tree) |

`file_grep`, `file_find` and recursive `file_list` skip `.git`, `node_modules`, `vendor`, `dist` and what the `.gitignore` files match (every directory's `.gitignore`, with `!` and `**`); the result ends with a line naming what was skipped, and `no_ignore: true` includes it (`.git` excepted).

- **Read-only by default.** Write tools exist only with `run --allow-write`, chat with `tools.allow_write: true`, or an ACP session in `default` mode. `--read-only` always wins. If the model calls a disabled tool, it is told how to enable it, and the call counts as a refusal.
- **Additional directories.** `run` and `chat` take `--add-dir <absolute directory>[:ro|:rw]` (repeatable, default `:ro`), and `SUGA_ADD_DIRS` adds more (entries separated by the OS path-list separator, `;` on Windows, which is how a job runner passes them). A `:ro` entry joins the session's read-only roots, like `tools.read_roots`, and suits the project root of a job whose `cwd` is one repository or a sibling module. A `:rw` entry also lets `file_write`, `file_edit` and `file_remove` write there, with the same approvals, dangerous-delete guard and `.git`/home/root refusals as the workspace; `shell_exec` still runs in the workspace. The directories are recorded in the session (`add_dirs`), so `--resume` / `--session-id` keeps them and a path named again takes the mode of this invocation. Under `--read-only` they are only ever readable (the flag is reported, the mode is kept in the session; only read-only directories can be authorized too). The context's environment section names each directory and its mode, so the model uses the file tools there instead of shell detours; a directory added in the middle of a chat is in the tools' reach from the next call on and reaches the model with the next turn's context update. Only existing absolute directories are accepted, `..` is cleaned, and a path outside the workspace and the added directories is still refused. ACP does not support added directories (a `session/new` with `additionalDirectories` is refused).
- **A directory asked for mid-session.** In chat, `:add-dir` / `:rm-dir` change the session's added directories while it runs (see above). Without them the model can still ask: when a file tool reaches a path outside the workspace, the read-only roots and the added directories, chat asks `授权访问 <directory>？[r] 只读 [w] 读写 [n] 拒绝` before the call runs (`chat.ask_outside_dirs`, default on) — the directory shown is the one the tool really resolved, symlinks followed, never a path the model described. An answer of `r` or `w` records the directory in the session (`source: ask`) and lets the call run; a `:rw` grant still gets the ordinary write confirmation afterwards. `[w]` is not offered in a `--read-only` session. With the question turned off, without a terminal, or in `run` and ACP, such a call is simply refused as before.
- **Chat asks first.** With `tools.approval: ask`, chat asks before each write or shell call and shows the full command, path or old/new text. Answer `y` (once), `a` (this tool for the rest of the process) or anything else to refuse. Three refusals end the turn.
- **Dangerous deletes.** A `shell_exec` command that deletes recursively (`rm -r`, `Remove-Item -Recurse`, `rd /s`, also inside `sh -c`, `cmd /c` and `pwsh -Command`) is stopped before approval when it targets `/`, `~` or `$HOME`, a drive root, the workspace or one of its parents, or a path that starts with a variable which, if empty, would leave it at the root (`"$X/"`, `"$dir\*"`); a glob over those directories (`rm ~/*`) counts without `-r`. Chat asks every time, even with `tools.approval: auto` or an earlier `a`, and only a typed `yes` runs it; `run` and ACP refuse it and point the model to `file_remove`. The trace records the reason (`danger=…`). This catches common slips, not a determined command: it is not a security boundary.
- **Background tasks.** `shell_exec` with `background: true` (write modes of `run`, chat and ACP) runs long builds, full test suites, servers or watchers while the model keeps working. Output goes line by line, redacted, to the session's outputs (`recall` reads its ref too). A task that ends before the model saw it leaves a notice that is added before the next model request (exit code, duration, size, last lines); chat waiting for input is woken by it and starts a turn (`tasks.wake_on_exit`, default true, which covers what a still running task reports as well). `run` reminds the model once when its answer leaves tasks running, then kills them at exit and names them on stderr. In ACP the tasks belong to the `suga acp` process: they keep running across prompts, the notice goes into the session's next prompt, `session/cancel` leaves them alone and they are killed when the connection closes. Limits: `tasks.max_running` (4 per session), `tasks.max_duration` (2h), `tasks.max_output_bytes` (64 MiB). The trace records a `task` event per task (its `kind` and, for a watch, its runs and changes); `--analyze` counts them and, per kind, the watch tasks and background Stop hooks. Design: docs/design/2026-10-13-background-tasks-design.md.
- **Watch tasks.** `shell_exec` with `background: true` plus `every` (seconds, at least 10) and/or `watch_paths` (globs relative to the workspace, `**` crosses directories and a pattern without `/` matches that file name at any depth) runs the command as a watch: once at the start and then on each tick and when a watched file changes (polled every 2s; a change runs the command after one more poll without further changes). Runs never overlap, each is capped by the call's `timeout` (and a run's own writes are no change of the watched files). The task output holds every run between `=== run N (trigger) HH:MM:SS ===` and `=== exit X ===`. The model is told about a run only when its exit code or output differs from the previous one (durations and timestamps ignored), and about the baseline run only when it fails, so it can fix code and learn from the next run that the tests went green. `task wait` on a watch returns once its next run is done, with that run's report; `task list` shows the runs and the last exit code; `task kill` stops the watch.
- **Background Stop hook.** With `hooks.stop_background: true` (chat only) the Stop hook runs as a `hook` task instead of a wait at the prompt: typing, deliveries and task wakes no longer interrupt it. A hook that answers `block` with a reason becomes the notice `Stop hook asks to continue: <reason>` — an idle chat wakes for it and starts the injected turn, a running turn gets it before its next model request. A new Stop kills the running one. The hook's timeout is `hooks.stop_wait_sec` + 2s when that is set, otherwise the task is bounded by `tasks.max_duration`; without a free task slot chat waits for the hook as before.
- **Parallel reads.** When one reply holds several `file_read`, `file_list`, `file_grep` or `file_find` calls, they run concurrently (`tools.parallel_reads`, default on). Every call still passes approval, taint tracking and tracing in order; only the reading itself overlaps.
- **Large outputs.** A tool result above `tools.max_output_bytes` is saved (redacted) to `$SUGA_HOME/sessions/<id>/outputs/`; the context keeps the head and tail (2000 bytes each) plus a ref such as `out:<session>:<hex>`. Read it with `recall`, search it with `session_search`. Before that, shell results are tidied (`tools.minimize_output`, default on): colour codes and progress redraws are dropped, runs of identical lines folded, and test and build output cut by output rules - one line per package plus a summary when everything passed, the failures with their messages and logs otherwise; the original is saved under a ref and the result says so. Built-in rules cover `go test`, `cargo test`, jest/vitest/mocha and `npm|pnpm|yarn|bun test`, pytest, Maven, Gradle, `git log`/`git diff`/`git status` and `rg`/`grep` hits; a rule drops lines, folds runs of noise, rewrites the result (`replace`), groups lines by a captured key (`group_by`), keeps the head and tail, and asks for its own size/saving gates (fields and format: [rules/](pkg/agentcore/tools/native/rules/)); `$SUGA_HOME/output-rules.yaml` and then `<workspace>/.suga/output-rules.yaml` replace a rule by name, add new ones, or switch one off with `enabled: false`. A command that pipes its output (`| grep`, `| Select-String`, `| tail` ...) is left to what it filtered: the rules do not apply to it. `file_read` pages by itself (up to `tools.read_page_bytes`, default 32 KiB per file and four pages per `paths` call) and is never saved.
- **Boundaries.** File tools go through `os.OpenRoot`, so they cannot follow symlinks out of the workspace. `shell_exec` kills the whole process tree on timeout. `web_fetch` checks the address it actually connects to, which also covers redirects. Every tool result is capped.
- **MCP.** Use `--mcp-config <file>` (Claude-style `mcpServers` JSON) or `mcp.servers` in the config. MCP calls are refused unless allowed by `tools.auto_allow`, or by `tools.read_only_allow` under `--read-only`. Large tool sets are deferred and loaded through `tool_search`.

Exact semantics: [Gofer setup and tools](docs/usage/gofer-personal-agent.md#内置工具与相关配置).

## Sub-agents

The `agent` tool hands one self-contained task to a sub-agent: a model run in a session of its own, with read-only tools, whose final answer is the report that comes back. Tasks that mean reading widely — tracing callers, comparing implementations, surveying a dependency — cost the parent context one report instead of every file read.

- **Two types.** `explore` (default) has the workspace read tools (`file_read`, `file_list`, `file_grep`, `file_find`); `research` adds `web_fetch` and `web_search`. A sub-agent cannot write files, run commands, ask the user or start another sub-agent, and it sees nothing of this conversation. The call's `description` names it in chat, in ACP and in the trace.
- **Background.** With `background: true` it runs as a task (kind `agent`): the call returns a task id at once, `task wait` waits for it, and the report is the task's output (a notice with its first lines tells you it ended). Start several to explore in parallel (they share the `tasks.max_running` slots with shell tasks). Read-only sessions have the `task` tool for this, since only its `list`/`output`/`wait`/`kill` are needed (backgrounding `shell_exec` still needs a write mode).
- **Limits.** `agents.max_steps` (30), `agents.max_tokens` (400000, counted as uncached input plus output, so a long cached context does not eat it) and `agents.timeout` (10m, a soft deadline with a 60s grace). Reaching one asks the sub-agent to wrap up and report what it has; the report ends with `[sub-agent <session> · N steps · in … / out … · <duration> · stop=<reason>]`, reason being `final`, `max_steps`, `max_tokens`, `timeout`, `cancelled` or `failed`. `agents.model` runs sub-agents on a cheaper model; `agents.enabled: false` leaves the tool out.
- **Usage and taint.** A sub-agent's model calls count in the run of the session that called it (stream-json and ACP `usage_update` include them, ACP while the prompt runs) and in its session total, which is the parent session plus its sub-agent sessions (`suga stats --session`). What the sub-agent read marks the parent session tainted like any other external read, so a `research` sub-agent (or one that read a file quoting the web) makes later memory writes need confirmation.
- **Sub-agent sessions.** Every call runs in a session of its own — `kind: agent`, with `parent_session_id`, `agent_type` and the turn and tool call that started it, titled with the description. `suga sessions` and `session_search` leave those sessions out by default; `suga sessions --agents` lists them, each naming its parent session. `suga trace <session>` reads one like any other session, and `suga gc` removes them with their parent.

## Skills

Suga scans `<workspace>/.agents/skills`, `<workspace>/skills`, `<SUGA_HOME>/skills` (default `~/.suga/skills`) and `~/.agents/skills` once at startup, in that order; a skill found earlier wins a name that appears again later. `<SUGA_HOME>/skills/suga-guide` is the built-in configuration and usage guide: the first run writes it there, and an upgrade refreshes it as long as every file is still the one suga wrote. The `.suga-builtin.json` marker beside it records what suga wrote (version and the hash of each file): a directory you edited, added a file to, or that has no marker at all (your own skill of that name) is never touched. If there are no more than `skills.list_max` skills, all of them are listed in the system prompt. Otherwise only workspace skills are listed with their description and the rest by name only (up to 3000 bytes of names; beyond that a count), so the model can load any of them by name or search with `skill(query=…)`. To put a skill's body into every prompt, mark it with `metadata: {always_load: true}` in its frontmatter, or list it in `skills.always_load`.

## Memory

Long-term memory shared across sessions, written by the model through the `memory` tool.

- **Four kinds**: `user` (who the user is, preferences), `feedback` (corrections and confirmed choices), `project` (goals, decisions, progress the code does not show), `reference` (where external resources live). Not stored: anything derivable from code or git, what rule files already say, session-local details, secrets. Procedures belong in skills.
- **Scopes and backends.** User memory lives in `$SUGA_HOME/memory/user` (files). Project memory picks its backend in this order: `memory.project.backend`; a `MEMORY.md` at the repository root (files, repository mode); a `.gofer/tracker` at the repository root (gofer); otherwise files under `$SUGA_HOME/projects/<key>/memory`, where `<key>` is the repository directory name plus a short hash of its full path (e.g. `suga-5cb0fa32`; also shown as the scope `project:<key>`). In repository mode the index is `MEMORY.md` and each entry is `.suga/memory/<id>.md`, so memory can be committed with the project. suga never creates the root `MEMORY.md`. With the gofer backend each project entry is a gofer memory tagged `suga`; only those are managed. `suga manifest` shows what was chosen and why.
- **Frozen index.** The memory index (titles only) goes into the segment context message and stays unchanged for the segment. Writes in this session show up in the next segment; a new segment refreshes it. Read a body with `memory get`.
- **Tainted sessions.** Once a session has read external content (`web_fetch`, `web_search`, MCP tools, `session_search`, `recall`, or the tools in `memory.taint_tools` / `memory.taint_on_spill`) it is marked tainted for good, and memory writes need confirmation (`memory.write_tainted`): chat asks (`y`, `n`, or `a` for the rest of the session), ACP sends a permission request, and `run` refuses. `deny` never writes, `allow` skips the question. Under `--read-only` (and ACP `read_only`) the tool only reads. Plain `run` may write memory, since it is suga's own state rather than the workspace.

## Sessions

- **Resume and handoff.** `--session-id` creates or reuses a named session. `--resume` requires an existing one; a missing session exits with code 4. `run --from <session>` starts a new session that inherits the old one's summary, plan and loaded tools.
- **Segments.** A session is a chain of segments. Each segment starts with a record (reason: start, threshold, `:compact`, idle, `--from`) that holds the context message and, after the first segment, a handoff: a summary for the current task, the last user requests verbatim and the refs that still matter. When the context nears the model window, or on `:compact`, a new segment starts; only the last complete tool call/result group is kept verbatim. Earlier segments stay in the database: fetch them with `session_search` and `recall`.
- **Interrupted turns.** A turn that ends `failed` or `cancelled` has already reached the workspace (it wrote files, ran commands, committed), so its record is no longer dropped: the next turn replays it up to its last complete tool call/result and adds one note naming the tools it ran and why it stopped. Only the dangling tail — a tool call that never got its result, and what followed — is cut, and the note says how many entries that left out. Compaction and context-update records of such a turn still do not take effect (the next turn recomputes them), and a steering message goes back to the input line instead of replaying.
- **History folding.** Each request re-sends the conversation so far, and most of it is the model's own reasoning and whole-file writes. With `context.fold_every` set (e.g. 10; default 0, off) and `context.fold_keep` (default 5), steps older than the last 5 are sent without their reasoning, and their string arguments over 1000 characters (a whole file written, a long edit) become a short note asking the model to re-read the file if needed. The fold point moves only every 10 steps, so the cached prefix stays valid in between. The stored session is unchanged; `suga trace` shows a `fold` line each time the point moves. In the T9 A/B this halved the context per request and cut the prompt total by 59% (docs/research/2026-10-11-suag-vs-omp-loop-analysis.md). It is off by default: rebuilding the cached prefix after each fold cost about a third of the uncached input in the P5 retest.
- **Idle consolidation (chat).** After `context.idle_after` (default 15m) without input, if the context has reached `context.idle_min_ratio` (default 0.5) of the threshold, chat starts a new segment in the background. It never fires during a turn, and typing cancels it.
- **Plans.** The `update_plan` tool records the model's plan. stream-json emits it as `plan` events, and ACP sends it as plan updates.
- **System prompt and segment context.** The system prompt holds only stable content (identity and working conventions), so it stays byte-identical across sessions and workspaces of one mode. Environment (OS, shell, workspace), project rules (one file per level, `rules.file`, default `AGENTS.md`, plus `~/.suga/AGENTS.md`), `--append-system-prompt`, the memory index, the skills list and deferred tools go into a context message at the start of each segment. A change inside a segment (for example edited rules) is appended as a "context update" message instead of rewriting earlier text. `--no-project-rules` skips project rules.
- **Delivery and hooks.** `suga send --session <s> <text>` (or `--text <text>`, not both) hands text to a running chat. `<s>` is a session ID, an ID prefix, or the short name every chat registers under — `<workspace directory>-<xy>`, like `suga-k7`, shown in its banner and by `suga ps`. The name is stored in the session and kept across resumes, so a resumed chat answers to the same one. `hooks.command` receives chat lifecycle events as JSON on stdin.

## Using with Gofer

Gofer launches `suga run` (CLI jobs) or `suga acp` (persistent sessions with per-call approval through `permission_policy`). For agent configuration, read-only and writable runs, the stream-json events and the denial contract, see [docs/usage/gofer-personal-agent.md](docs/usage/gofer-personal-agent.md).

## Observability

```text
suga trace <session> [--turn <id>] [--json]       # timeline: model calls, tools, denials, plans
suga sessions [keywords] [-n 10] [--since 7d] [--until 2026-10-01] [--cwd .] [--agents] [--json]  # sessions, newest first; keywords match title, id, directory, model or the conversation; --agents lists sub-agent sessions too
suga trace <session> --analyze [--json]          # loop summary: steps, parallel calls, re-reads, repeated commands, tests after the first pass, sub-agents
suga trace <session> --web [--addr 127.0.0.1:0]  # local web page: timeline (task bars, labelled task notices, sub-agent rows with the command for their own trace), details, context composition, analysis, this machine's environment (Ctrl-C to stop)
suga stats [--session <id>] [--since 7d] [--json] # calls, latency, tokens, cache hits
suga export <session> [--redact] [-o <file>]      # entries and events as jsonl
suga gc --older-than 30d [--apply]                # list (default) or delete idle sessions
suga ps                                           # running chat processes, with their short names
suga manifest [--json] [--model <p/m>]            # models, tools, MCP, skills, memory backends, output limits
```

Tool lines show the exit code (shell), the bytes that entered the context, a spill marker and a redacted argument summary; an `agent` line (a sub-agent call) adds the session it ran in, its type, the steps it took with the sub-agent's own tool calls, its tokens and cost and why it stopped (`sub=<session> type=explore steps=12 calls=5 in=85k(cache 60k) out=3k cost=$0.0123 stop=final`), while the task line of a background sub-agent shows `agent steps=N calls=M`; model lines show how many tool calls the response issued (`calls=N`), `truncated` when the output limit cut the reply off, `retries=N(reason, waited Xs)` when the request was retried, the cached input tokens (`cached=N`) and, when a request did not extend the previous one, why and how much earlier content was sent again (`prefix=fold(rebuilt=12k)`; reasons fold, segment, system, tools, rewrite). `--analyze` derives from the same events: steps and parallel steps, tool counts and failures, files read more than once and reads of files the session had just written, edits per file, identical shell commands run again, test runs and how many came after the first passing one (a run counts as passing only when its output reports no failure, whatever the exit code), the phases in model calls (exploration before the first write, first write to the first passing test, after it), edit steps and how many made a single change, shell runs that exited 0 but wrote to stderr, the uncached input split into content new since the previous request, earlier content sent again after a prefix break (by reason) and what the provider left uncached although the prefix allowed it (estimated from request sizes), spills, folds, compactions, model retries, the slowest model calls and what the session's sub-agents cost (the calls, steps, tool calls, tokens, cost and time of `agent_calls`, `agent_steps`, `agent_tool_calls`, `agent_input_tokens`, `agent_cache_read_tokens`, `agent_output_tokens`, `agent_cost_usd` and `agent_ms`, with `agent_stops` counting why they stopped). For background tasks it adds how much of their run time the loop spent in model or tool calls instead (`background_overlap_ms`, the waiting saved, counting commands run in the background, not watches or Stop hooks; foreground calls that overlap count once), how often `task wait` blocked the loop and for how long, and how many of those waits came right after the task was started (`immediate_waits`, a background task used as if it were foreground), and per kind the numbers of the session: the watch tasks with their runs and changes (`watch_tasks`, `watch_runs`, `watch_changes`) and the runs of the background Stop hook (`stop_hooks`). A `task` line (the end of a background task) names the task's kind: a watch adds `runs=N changes=M` or its last state, a Stop hook shows its summary, an agent task the steps its sub-agent ran. Tool lines also show `+added/-removed` lines for edits and `approval=user(wait=3.2s)` when a person was asked. A `context` line per turn lists what the first request of the turn is made of (chars of the system prompt, tools with their count and MCP share, environment, rules, memory index, skills, deferred tools, handoff, history, hook context, the input) and the estimated tokens against the window; `hook` lines record each hook run (event, duration, block decision, injected context). Turn lines carry the input length and whether it was injected rather than typed. `suga trace` also shows a `turn_context` line per turn (model, mode, tool set hash, rules and memory index hashes, tainted), a line for each segment break (`segment=#N reason=... tokens=before->after`) and `schedule` events (chat idle consolidation: fired, done, cancelled, skipped). A `session recovered` line records a session a dead process left in `running` and this one took back to `open` (`turn=` is the interrupted turn, which is recorded `cancelled`): it is what lets `chat --resume` and `run --resume` start a new turn. `suga stats` shows cost per model (from the provider, or from `price` in the config) and, with `--json`, tool output bytes (`raw_bytes`, `inline_bytes`, `spilled`).

`run --output-format stream-json` prints a `usage` line after every model call, with the run's running totals: `input_tokens` (cache excluded), `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `total_tokens`, `cost_usd` and `tool_calls`. `turn_end` and `result` carry the same `usage`, so a consumer can enforce a budget mid-run. A `retry` line (`reason`, `attempt`, `wait_ms`, `restart`) announces a model request retried after a transient failure; with `restart: true` the message's `message_delta` text so far is void and the message streams again from its start. Chat prints such a retry as a `↻` notice line, `run` prints it to stderr and ACP sends it as a thought chunk. ACP sends `usage_update` at the same moments ([details](docs/usage/gofer-personal-agent.md#acp-用量上报)). A turn that ended with a wrap-up answer instead of a normal one marks it in the closing `result` line with `wrap_up` (`"max_steps"` when it hit the step limit, absent otherwise); text mode prints that reason on stderr, so a short answer is not taken for a finished one — or for a timeout.

Process diagnostics go to `$SUGA_HOME/logs/suga.log` (0600, appended by every run, never rotated) and to nothing else: what a person needs is printed by the run itself (session id, model, a retry, a wrap-up reason), and Gofer reads stdout as protocol, so free-form log lines would only clutter the terminal or the job log. `SUGA_DEBUG=1` turns on debug records and a copy on stderr (for a Gofer agent that is `env: {SUGA_DEBUG: "1"}`); if the log file cannot be opened, stderr gets the records either way.

## Development

```bash
go test -race ./...     # unit tests
make smoke-chat         # PTY end-to-end chat tests incl. chat_memory and chat_idle (Linux/macOS, Python 3)
go run ./scripts/eval --fake --bin tmp/smoke/suga   # task evals, see scripts/eval/README.md
make build-all          # cross-compile to dist/
```

The eval has multi-turn tasks (`prompts` in `task.yaml`, one session) and reports `first_call_uncached` (FIRST column: uncached input of the first main model call). `--probe-prefix` runs three probes of the prefix cache: same workspace, a different workspace, and a control with a random nonce in the system prompt. `--agent omp` runs the same tasks on omp for comparison.

- `cmd/suga`: entry point; `internal/cli`: one file per command.
- `internal/wiring`: builds providers, tools, skills, the system prompt and the runner for CLI and ACP.
- `internal/personal`: turns, segments, handoff and events; `internal/personal/store` is the SQLite store.
- `internal/chat`: terminal chat; `internal/acpserver`: the ACP server.
- `pkg/agentcore`: the reusable layers below the app, independent of `internal/*` ([README](pkg/agentcore/README.md)): the kernel (model/tool loop, run state, transcript) plus `llm` (providers), `schedule` (in-process After/Every/Idle timers), `tools` (registry, approval, deferred tools), `tools/native` (built-in tools), `tools/mcp` (MCP client), `skills`, `memory` (store interface, governance, router; `memory/files` and `memory/execstore` backends), `redact` (secret and invisible-text cleaning) and `extproc` (exec protocol v1 and credential stripping for external commands).

Release notes are in [CHANGELOG.md](CHANGELOG.md); design notes and plans are in [docs/](docs/README.md). CI runs tests on Ubuntu and Windows with Go 1.26 and stable. The old control plane (team, cron, orchestrator) is kept at the `v0.1.0` tag.
